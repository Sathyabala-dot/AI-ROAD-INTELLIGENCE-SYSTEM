## 1. Project Overview

Module 2 sits between Module 1 (computer-vision road feature detection)
and Module 3 (Web GIS dashboard). It takes structured road-observation
data, predicts a **Road Health Score (0–100)** using a trained ML model,
classifies road condition, and produces **congestion**, **accident risk**,
and **maintenance priority** outputs, storing everything in
PostgreSQL/PostGIS and serving it via FastAPI.

```
Module 1 → Structured JSON → FastAPI → Validation → Feature Engineering
    → ML Health Model → Health Score (0-100) → Condition Class
    → [Congestion | Accident Risk | Maintenance Priority]
    → PostgreSQL/PostGIS → Module 3 GIS Dashboard
```

## 2. Module 2 Responsibilities

| Component | Approach | Why |
|---|---|---|
| Road Health Score | **Machine Learning** (RandomForestRegressor) | Genuine numeric prediction target, tabular data suits it well |
| Condition Classification | Rule-based thresholds on the score | Project-defined bands, documented, not an external standard |
| Congestion | **Rule-based** | No genuine congestion ground-truth in the dataset — see §16 below |
| Accident Risk | **Rule-based** | No sufficiently large/verified accident dataset — see §17 below |
| Maintenance Priority | **Rule-based** scoring | Combines the above three outputs transparently |

This mixed ML + rule-based design is intentional and matches the project
constraint: *never fabricate an ML model where no genuine target exists.*

## 8. Model Training

```bash
python training/train_health_model.py
```

Pipeline: load → validate → clean (drop duplicates/null road_id) →
feature-engineer (`damage_density`, `pothole_ratio`) → select target →
select available features → build `ColumnTransformer`
(median-impute+scale numeric, most-frequent-impute+one-hot categorical)
→ **GroupShuffleSplit by `road_id`** (80/20) to prevent the same road
leaking across train/test → train `RandomForestRegressor` → evaluate →
save.

**Why GroupShuffleSplit and not a plain random split:** the same road_id
appears multiple times (repeated observations). A random row-level split
would let the model see the same road in both training and test data,
inflating apparent accuracy. Grouping by `road_id` avoids this leakage.

## 9. Road Health Score Target — CASE B (derived)

The dataset has **no genuine labelled health score**, so
`health_score_target.py` computes one from a documented, reproducible
weighted-penalty formula (100 minus penalties for potholes, damage
count/severity/area, low detection confidence, maintenance neglect, and
recent rainfall). Full weights and reasoning are commented in that file.
**This is a project-derived target, not an official government standard.**

## 10. Model Selection

**RandomForestRegressor** was chosen over XGBoost/LightGBM because:
- The feature set is small/medium tabular data — no need for gradient-boosted complexity.
- It handles mixed numeric + one-hot categorical features robustly without heavy tuning.
- `feature_importances_` gives direct explainability for the viva.
- No extra heavy dependency (XGBoost/LightGBM) is required.
- Fast to train and demonstrate live during a viva.

## 11. Model Evaluation — ACTUAL results from this run

```
Trained on: data/raw/sample_road_observations.csv (SYNTHETIC)
Train rows: 386   Test rows: 96   (48 / 12 unique roads)

MAE  = 2.4354
RMSE = 2.9610
R²   = 0.9596
```

**Top feature importances:** `days_since_maintenance` (0.753),
`damage_count` (0.119), `pothole_count` (0.050), `damage_severity` (0.035),
`damaged_area_percent` (0.015).

⚠️ **Honest caveat for your report:** these numbers look very strong
because the target itself is a **deterministic formula of these same
features** (see §9) — the model is learning a formula, not real-world
noise, so high R² here is expected and does **not** represent real-world
predictive accuracy. State this explicitly in your report. Once trained
on a real, independently-labelled dataset, expect these numbers to look
different (typically lower R², higher error) — that is normal and honest.

## 16. Congestion — Rule-Based (documented reasoning)

No genuine congestion ground-truth exists in the dataset (only a
`vehicle_count` proxy). Per the project constraint, no ML model is
fabricated. `services/congestion_service.py` computes a
volume/capacity ratio using documented per-lane capacity assumptions by
road type, mapped to Low/Medium/High/Severe. Labelled explicitly as
**"Rule-Based Congestion Estimation"** in every API response.

## 17. Accident Risk — Rule-Based (documented reasoning)

No sufficiently large/verified historical accident dataset exists. A
weighted combination of health score, damage severity, traffic volume,
weather, and historical accident count produces Low/Medium/High.
Labelled explicitly as **"Rule-Based Accident Risk Estimation."**

## 18. Maintenance Priority — Rule-Based

Combines health score + accident risk + congestion + damage severity
into a points system → High/Medium/Low. Full point logic documented in
`services/maintenance_service.py`.

## 24. Limitations

- Trained/evaluated on synthetic data — real-world accuracy is unknown until real data is used.
- No live CCTV, IoT, or crowdsourced image feed — predictions run on whatever observations are supplied, not continuous monitoring.
- Congestion and accident risk are rule-based, not ML, due to lack of genuine labelled targets.
- Congestion capacity assumptions (`services/congestion_service.py`) are illustrative, not traffic-engineering-calibrated values.

## 25. Future Scope
